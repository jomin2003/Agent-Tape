# Design

This document explains why `agenttape` is shaped the way it is. The
[research brief](../research/deterministic-replay-and-rollback-for-ai-agents.md)
establishes the problem; this is the response to it.

---

## 1. The premise

A replay library can only *control* two of the seven layers of non-determinism in
an agent — ambient state (clock, RNG, env, filesystem) and scheduling. The other
five (sampling, kernel numerics, hardware, MoE routing, external state) cannot be
controlled by anything running on the client, because they happen on someone
else's machine.

So they must be **captured**.

> **A deterministic replay system is, first and foremost, a complete recording
> system. Its correctness ceiling is the completeness of its instrumentation.**

Almost every design decision below follows from taking that sentence seriously.

## 2. The tape

```
runs/triage.tape/
├── manifest.json     # small; readable without touching the event log
├── events.jsonl      # one canonical-JSON event per line, append-only
└── blobs/<sha256>    # content-addressed payloads above the blob threshold
```

### Why a directory and not a single file

Because `manifest.json` and `events.jsonl` have different access patterns. Listing
ten thousand runs should read ten thousand small files, not ten thousand event
logs. `Tape.describe(path)` reads only the manifest.

### Why JSONL

Append-only, streamable, greppable, diffable, and requires no database. A tape is
something a human opens in an editor at 2am, and that property is worth more than
compactness.

### Why the hash chain

Each event's `hash` covers its body *including the previous event's hash*. Editing
or reordering any event invalidates every event after it. `verify()` walks the
chain and compares the head against the manifest digest.

This is not paranoia about attackers. It is about the much more common failure:
not knowing whether the tape you are debugging from is the tape that was recorded.
Tapes get copied, truncated by `scp`, edited by a well-meaning colleague who
redacted something, and regenerated by a script. The chain turns "I think this is
the right file" into a checkable claim.

### Why the hash covers the *stored* body, not the logical one

The obvious design is to hash the logical content and let blob encoding be a
storage detail. That design has a flaw: verifying a tape then requires resolving
its blobs, so a tape with a damaged blob store cannot be checked for tampering,
and the two failure modes become indistinguishable.

Hashing the stored form makes integrity verification a purely local operation over
the event log. Blob *contents* are still covered — a blob reference embeds the
SHA-256 of the bytes — but transitively, and checkably in isolation.

The cost is that the hash depends on the blob threshold. That is acceptable,
because the threshold is recorded in the manifest, and because a tape re-encoded
with a different threshold is genuinely a different tape.

### Why `fsync` before returning

`Tape.append` writes the line, flushes, and `fsync`s **before** the caller
receives the value.

The alternative ordering — return first, persist later — produces a *holed* log
after a crash: an effect that happened with no record of it. A holed log is worse
than useless, because it is silently wrong. A truncated log is recoverable: the
tail event is discarded with a warning, and everything before it is intact.

One `fsync` per event is not free. It is the price of the log not lying.

### Why failures are events

A tool that raised is recorded with `status="error"` and a portable error record
(type name, module, message, repr). On replay the same exception type is re-raised.

This matters more than it looks. Agent control flow branches on exceptions:

```python
try:
    result = session.tool("flaky_api", [payload], fn=call_api)
except TimeoutError:
    return fall_back_to_cache()
```

If replay could not reproduce the `TimeoutError`, it would take the happy path and
the replay would be a different program. Errors are not gaps in the recording;
they are the most interesting part of it.

## 3. Matching

### Sequence-primary, fingerprint-validated

The *n*-th call of a replay must equal the *n*-th call of the recording, and the
request fingerprint must match.

The alternative — matching by request key alone, in any order — tolerates
concurrency and legitimate reordering, and it fails in exactly the situation you
most need it to work. An agent that is *nearly* deterministic will find a
plausible-but-wrong response and continue, producing a replay that looks
successful and is not.

Positional matching makes every deviation a real deviation. Validating the
fingerprint as well means the error can say *what* changed, and the library can
generate a unified diff of the recorded and observed requests:

```
expected #2 model:gpt-4o {"messages":[{"content":"one"}],"temperature":0.0}
observed model:gpt-4o (same call, different arguments)
  --- recorded
  +++ replayed
  @@ -1,4 +1,4 @@
    {
  -  "content": "one"
  +  "content": "TWO"
    }
```

### Replay never guesses

If a call cannot be matched, the engine raises. It does not fall through to a live
system, and it does not serve a nearby response.

This is the property that makes the library worth using. A replay engine that
guesses is worse than no replay engine, because it manufactures false confidence —
and false confidence in a debugging tool is the most expensive kind.

`strict=False` and `on_divergence="warn"` exist as escape hatches for refactors
that legitimately reorder independent calls. They record every divergence, and
`session.verified` goes false. They are not the default, because tolerance is
precisely the property you do not want while debugging.

### Three failure modes, three exceptions

| Situation | Exception |
|---|---|
| The call does not match the recording | `RequestMismatchError` |
| The run is longer than the recording | `TapeExhaustedError` |
| The run is shorter than the recording | `UnconsumedEventsError` |

All three subclass `DivergenceError`, so `except DivergenceError` catches every
replay failure.

The third one deserves emphasis. A replay that finishes early and says nothing
looks like success. It is not: it means the agent took a shorter path, which is
exactly the kind of regression replay exists to catch.

### O(1) memory

Replay streams the event log rather than loading it. Events are yielded as they
are parsed, and the cursor moves forward. This is what makes replay viable on
multi-megabyte tapes, and it is why `strict=True` is the default mode: it needs a
buffer of exactly one event.

Non-strict mode may buffer up to `lookahead` events while searching, which is
bounded and configurable.

## 4. Deterministic primitives

### Clock

Every reading is recorded, including the full datetime **with its UTC offset**.
Recording the offset rather than the epoch means replaying on a machine in a
different timezone yields exactly what the original run saw, instead of the same
instant rendered in a different local time.

`sleep()` actually sleeps while recording — the recorded duration is what really
elapsed — and returns immediately while replaying. Replaying an agent with
exponential backoff should not take minutes.

### Randomness

`DeterministicRandom` seeds from the tape's recorded seed **and** records every
draw.

Seeding alone is sufficient if the agent makes the same number of draws in the
same order. Recording makes the guarantee robust to code changes — which is
exactly the situation in which you need it, since you replay a tape *because*
something changed.

Only two primitives are intercepted: `random()` and `getrandbits()`. Every other
`random.Random` method — `choice`, `shuffle`, `sample`, `gauss`, `randint` — is
implemented on top of those two in the standard library, so the whole surface is
covered, including methods that do not exist yet.

## 5. Canonical serialisation

Everything that is compared or hashed goes through `agenttape.canonical`. Two
semantically identical values must produce byte-identical output, on any machine,
in any process.

- Mappings are key-sorted, with no insignificant whitespace.
- Set elements are sorted **by their own canonical encoding**. Python's iteration
  order for sets depends on `PYTHONHASHSEED`, so trusting it would make
  fingerprints vary between processes.
- `float` uses Python's shortest round-tripping `repr`. NaN and infinities are
  encoded symbolically, because JSON has no representation for them.
- Non-JSON-native types are tagged with a single reserved key, so the encoding is
  self-describing and reversible.
- Anything else **raises** rather than falling back to `repr()`. A default
  `repr()` contains a memory address, which would make fingerprints
  non-reproducible in a way that only shows up on a different run. Failing loudly
  at the boundary is much better than producing a tape that cannot be replayed.

There is a test that runs the encoder in subprocesses with different
`PYTHONHASHSEED` values and asserts the output is identical.

## 6. Rollback

An agent's effects live in the outside world: a payment moved, an email sent, a
ticket closed. You cannot rewind those by restoring a process image, and you
usually cannot invert them — a refund is a new transaction, not an undo.

This is the classic saga problem. The standard answer is compensating
transactions, which must be idempotent because retries are guaranteed.

`agenttape`'s contribution is small but specific: **the compensation plan is
recorded in the tape, alongside the effect.**

```python
session.effect("charge_card", charge, args=("acct_1", 100),
               compensate=("refund", {"reason": "booking aborted"}))
```

Three consequences:

1. **Rollback is replayable.** `session.rollback()` walks the recorded effects in
   reverse and applies their plans. Replaying the tape reproduces the same
   sequence of compensations *without invoking the compensators* — replaying a
   tape that issued a refund does not issue a refund.

2. **Rollback is auditable.** The plan is data on disk, not logic in the caller's
   head. You can read what would have been undone, and why, after the fact.

3. **Rollback is idempotent by construction.** Already-compensated effects are
   skipped, so a retried rollback is safe.

Compensators are addressed **by name**, not by reference, because the tape must be
replayable in a process where the original callable does not exist. A name in the
tape plus a registration in the replaying process is the only portable
arrangement.

What this does *not* do: guarantee that a compensation fully undoes its effect.
There is no general theory of "how undone" an effect is, and the research brief
lists that as an open problem. `rollback()` returns a per-effect record with
`ok` and either `result` or `error`, so a partially-failed rollback is visible
rather than silent.

## 7. Counterfactual replay

Fork the recording, replay the prefix, and continue live into a new tape:

```python
with agenttape.replay("runs/x.tape", on_exhausted="live",
                      fork_to="runs/x-counterfactual.tape") as session:
    run_agent_with_a_change(session)
```

`Tape.fork` copies the prefix **verbatim** — the same bytes, the same hashes, the
same chain links — so the fork's prefix verifies against the original's. The fork
is left open, the live tail appends to it, and the original is never touched.

When the recording runs out, the session writes a `fork` event marking the branch
point and switches to recording. That event is tape metadata rather than an agent
call, so replay skips it; a forked tape replays like any other.

`diff(original, fork)` then tells you exactly where the two runs parted.

## 8. What was deliberately left out

| Left out | Why |
|---|---|
| A CLI | It is a library. A CLI is a separate package that imports this one. |
| Runtime dependencies | A replay engine sits under the agent. Every dependency it adds is inherited, and every dependency is a potential source of non-determinism. |
| Concurrency and streaming replay | Unsolved in the field. Streaming chunk boundaries depend on network scheduling, and concurrent calls have no canonical order. Pretending otherwise would be worse than declaring the boundary. |
| Automatic instrumentation of HTTP clients | Convenient, and it would silently create the illusion of completeness. A transport-layer proxy cannot see in-process state; an in-process wrapper cannot see a raw socket. Better to make the boundary explicit and visible. |
| A hosted service, a UI, a marketplace | Out of scope. |

## 9. Where this goes next

The research brief names ten open problems. The ones most likely to move next,
and most tractable from inside this codebase:

1. **A completeness check.** Today, "is this tape complete?" is answered by
   failing to find a hole. A static or runtime check that *proves* a boundary is
   wrapped would be the single biggest improvement in trustworthiness.
2. **Replay-preserving redaction.** Tapes contain prompts and personal data;
   redaction currently breaks the hash chain. A redaction scheme that preserves
   replay fidelity is genuinely hard and genuinely needed.
3. **A shared replay-fidelity benchmark.** Comparing engines today means trusting
   each one's own numbers.

Contributions that move any of these forward are welcome. See
[CONTRIBUTING.md](../CONTRIBUTING.md).
